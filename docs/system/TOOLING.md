# Capability routing and local tooling

This document explains how a run discovers and routes skills, MCP servers, external tools, and repository-owned validation. [`AGENTS.md`](../../AGENTS.md) owns orchestration, [`ANTIGRAVITY.md`](ANTIGRAVITY.md) owns Antigravity-specific runtime behavior, [`RUNBOOK.md`](RUNBOOK.md) owns execution order, and the project specifications remain authoritative in their domains.

## Capability boundaries

- **Repository rules** in [`.agents/rules/`](../../.agents/rules/code-quality.md) are permanent constraints. They are always active and are never selected as skills.
- **Skills** are readable instruction packages discovered in the current agent environment. They supply expertise and methods, not external access.
- **MCP servers and external tools** are runtime capabilities discovered in the current environment. They may supply external data, applications, or interactive access, but they are not skills or website dependencies.
- **Local tooling** is installed with this repository and provides deterministic checks regardless of optional skill or MCP availability.

The repository does not vendor third-party skills or MCP servers. A name in this document describes a logical capability unless the preflight confirms an exact installed and readable package or callable tool. Never claim that a capability is installed from its name alone, and never hardcode a machine-specific installation path.

## Mandatory capability preflight

Follow the preflight in [`AGENTS.md`](../../AGENTS.md) after readiness review:

1. Enumerate skills the current environment can actually discover.
2. Enumerate visible MCP servers and external tools.
3. Map only relevant discoveries to the logical capabilities below.
4. Verify selected skills by exact name, readable `SKILL.md`, and phase relevance.
5. Verify selected MCP capabilities only when the server is installed and enabled, its tools are visible, and a harmless read-only discovery or health call succeeds.
6. Choose the smallest useful set: normally one primary skill for a phase and, if it adds a different perspective, one critic.
7. Assign a local fallback to every unavailable or unverified optional capability.
8. Continue unless a genuinely required capability has no safe fallback.

Use these states consistently:

| State                    | Meaning                                                                                                                                                                      |
| ------------------------ | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `SELECTED_VERIFIED`      | Selected for this run and verified under the skill or MCP rules above.                                                                                                       |
| `AVAILABLE_NOT_SELECTED` | Discovered but not needed, or visible without a safe read-only verification path. It must not be used or claimed as verified yet.                                            |
| `UNAVAILABLE`            | Not discoverable, not readable, not enabled, or not reachable.                                                                                                               |
| `FALLBACK_ACTIVE`        | The documented repository or local method is being used instead.                                                                                                             |
| `BLOCKED_REQUIRED`       | The owning project specification requires the capability and no safe fallback can satisfy it. This is the only state that stops autonomous execution for capability reasons. |

Never use generation, writes, project creation, deletion, publishing, or another mutation as an MCP health check. If no safe read-only probe exists, use `AVAILABLE_NOT_SELECTED` and `FALLBACK_ACTIVE` until an authorized real use succeeds.

Keep the report brief and evidence-based:

```text
Antigravity capability preflight

SELECTED_VERIFIED
- Design intelligence: <exact readable package or none>
- Visual exploration: <verified Stitch when routed or local fallback>
- Motion: <exact readable package or none>
- Browser verification: <exact safely probed capability or none>

AVAILABLE_NOT_SELECTED
- <capability and reason, or none>

UNAVAILABLE
- <optional capability or none>

FALLBACK_ACTIVE
- <capability: local method>

BLOCKED_REQUIRED
- none
```

## Preferred Antigravity skill routing

This is the canonical inventory and intent-routing source. The listed names form the user's preferred Antigravity/Gemini capability profile; they are not permanent proof of installation. Every run must still discover the exact skill, read its `SKILL.md`, confirm relevance, and assign it to one primary phase or bounded specialist role before reporting it as `SELECTED_VERIFIED`. Actually follow the selected instructions during that phase.

An exact skill name in the current user prompt is a strong selection signal, but it does not outrank the authority hierarchy or bypass discovery. Natural-language requests are mapped semantically through the router below. Select the smallest useful set, avoid competing creative directors, and leave unrelated discovered skills as `AVAILABLE_NOT_SELECTED`.

If direct user intent changes a recorded project decision, the direct instruction wins and the agent must reconcile the owning project document before implementation. For example, “use scroll animations” updates the motion direction in `DESIGN.md`; it does not permit a skill to operate against an older contradictory setting.

### Avoid skill overload

Installed does not mean selected. A normal showcase will often need only this verified bundle:

```text
ui-ux-pro-max
frontend-design
design-taste-frontend
emil-design-eng
transitions-dev
transitions-polish
vercel-react-best-practices
verification-before-completion
```

Add `brainstorming`, `brand`, `design`, `design-system`, `banner-design`, `web-design-guidelines`, React composition, debugging, testing, code-review, Teamwork, or Git skills only when the project or observed evidence actually requires them. Normally choose one design-intelligence primary, one frontend implementation primary, one visual critic, only the relevant motion specialists, one React quality reviewer, and final verification. Stitch is a tool used under that expertise; it is not another skill and does not justify activating the rest of the inventory.

### Default phase ownership

```text
Current user intent + project specifications
→ discover and read the smallest relevant design-skill bundle
→ establish a short design hypothesis
→ use verified Stitch for two meaningful visual directions when routing and DESIGN.md permit
→ design-taste-frontend and any distinct bounded critic evaluate the directions
→ select or synthesize one coherent visual system
→ selected decisions persisted in DESIGN.md and the concepts handoff
→ frontend-design implementation with bounded ui-styling/design-system specialists
→ React quality review
→ emil-design-eng motion direction
→ transitions-dev implementation
→ transitions-polish motion review
→ responsive and accessibility refinement
→ implementation visual QA against the persisted direction
→ debugging and corrective iteration when failures occur
→ verification-before-completion
→ Antigravity browser verification
→ mandatory Playwright + axe baseline
→ one final pnpm qa
```

The sequence assigns expertise, not project authority. Stitch never becomes a parallel source of truth or the owner of application architecture, motion skills cannot increase animation density beyond `DESIGN.md`, browser tooling supplies observations, and Playwright supplies deterministic evidence rather than aesthetic judgment.

## Skill-guided Stitch workflow

Use this conceptual model consistently:

```text
Skills = expertise, methods, constraints and review criteria
Stitch MCP = optional external visual exploration and UI concept surface
Project documents = authoritative brief, content, direction and acceptance contract
DESIGN.md + concepts handoff = durable record of the selected direction and rationale
Frontend code = implementation of that recorded direction
Browser and local QA = verification of the implementation
```

Stitch can lead visual exploration without becoming a hard dependency or a permanent source of truth. Direct user instructions and the owning project specifications remain authoritative. Stitch-generated frontend code may be inspected for visual intent, but it must never be copied blindly into production; rebuild the selected direction in the repository's real Next.js/React stack and follow all engineering, clean-code, accessibility, and acceptance contracts.

### Before Stitch exploration

Select the smallest relevant bundle, discover each exact skill, and read every selected `SKILL.md` before the first Stitch call. Record the selected skills at the beginning of the run.

- Creative discovery may use `brainstorming`, `brand`, `design`, and a bounded `design-taste-frontend` lens only when the brief needs them.
- use `ui-ux-pro-max` as the primary design-intelligence guide for hierarchy, UX, typography, color, responsiveness, and anti-pattern avoidance;
- use `frontend-design` as the implementation-feasibility and frontend-implementation guide;
- use `emil-design-eng` for interaction and motion thinking, not as a competing visual director;
- use `ui-styling` only for a focused surface and `web-design-guidelines` for a distinct convention or accessibility review;
- use `design-system` only when reusable tokens, primitives, or behavior justify it;
- use `banner-design` only for an actual campaign or banner deliverable.

Before calling Stitch, write a short design hypothesis derived from `SITE.md`, `DESIGN.md`, `CONTENT.md`, direct user intent, supplied references, and the selected skill instructions. It should state the brand thesis, central creative idea, required routes and sections, content hierarchy, typography direction, composition grammar, image direction, responsive requirements, motion intent, signature moments, anti-patterns, and implementation constraints. Do not send a vague “make a beautiful website” request.

### During Stitch exploration

Antigravity—not Stitch—applies the selected skill instructions while operating Stitch. For an ordinary fresh showcase, create two directions that differ meaningfully in composition, typography, rhythm, imagery, hierarchy, or interaction model. Use three only when the design is especially important or genuinely unresolved. Superficial palette swaps are not separate directions.

Stitch is normally selected when starting a completely new showcase, creating a new visual identity or major page concept, exploring multiple directions, interpreting supplied screenshots, sketches, references, or wireframes, answering a strong editorial, experimental, premium, or unconventional `DESIGN.md` brief, or responding to an explicit Stitch request.

Stitch is normally not selected for small content edits, isolated bug fixes, dependency maintenance, lint/type/build/test repairs, minor responsive fixes, routine refactoring, or implementation of an already approved and sufficiently specified design.

### Evaluation and bounded synthesis

Evaluate every direction against `DESIGN.md`, `SITE.md`, the actual content hierarchy, accessibility, responsive transformations, asset feasibility, implementation constraints, and the repository's anti-generic rules. Use `design-taste-frontend` as the primary aesthetic critic, `web-design-guidelines` for a distinct usability, accessibility, and convention review when valuable, and `ui-ux-pro-max` only for unresolved hierarchy or UX validation. Select or synthesize one coherent direction; critics must not invent an uncontrolled new set of concepts.

### Durable handoff before implementation

Before frontend implementation begins, record the selected visual direction, typography roles, palette logic, grid and composition behavior, image direction, responsive transformations, motion personality, signature moments, relevant rejected alternatives, and implementation constraints in `DESIGN.md`. Add the Stitch project and screen identifiers or links, prompts, rejected alternatives and reasons, asset assumptions, implementation deviations, responsive interpretation, and motion opportunities to [`concepts/`](../../concepts/README.md). Store permitted references, exports, and production assets in their documented local locations. Never leave the build dependent on a temporary Stitch URL, generated code, unrecorded conversation output, or an inaccessible external artifact.

### Motion handoff

After the Stitch direction is persisted, `emil-design-eng` interprets it as a frontend motion system. Use `transitions-dev` for required page, state, element, reveal, and scroll transitions, then `transitions-polish` for final timing, easing, interruption, reduced-motion, and performance refinement. Stitch may communicate motion intent and visual states; application code owns the implementation and browser verification. Motion-intent phrases listed above route to these skills after visual exploration. “GSAP-level” is a quality signal, not dependency-installation authority; [`STACK.md`](STACK.md) remains authoritative.

## MCP and external-tool routing

MCP tools are optional runtime capabilities. The repository installs none, and a copied project must remain implementable and verifiable without them whenever a local fallback exists. Installation or connection makes tools available to Antigravity, but the model still selects them by relevance and permission. Follow the configuration boundaries in [`ANTIGRAVITY.md`](ANTIGRAVITY.md); the intended reusable Stitch connection belongs in Antigravity's global configuration rather than a copied repository, and neither location may place credentials in version control.

### Stitch policy

Use the globally configured server named `stitch` as the preferred optional visual-exploration MCP when its tools are visible, a harmless read-only probe succeeds, `DESIGN.md` permits new exploration, the routing above calls for it, and the user has not disabled it. Do not install Stitch, add a project-local server entry, edit user/global configuration, make it a repository dependency, or store credentials or machine-specific paths.

- **Normal fresh showcase:** prefer two meaningfully different Stitch directions after the selected creative and UI skills are read.
- **Especially important or unresolved design:** use three directions only when their additional comparison value is real.
- **Existing approved design or implementation-only task:** do not call Stitch merely because it is available.
- **Explicit user request or opt-out:** treat either as a strong routing signal, reconcile it into `DESIGN.md`, and still respect capability verification and authority.

The narrow optional one-time Antigravity project permission `mcp(stitch/*)` permits autonomous use of Stitch tools without repeated MCP approval prompts. It must not be replaced with `mcp(*)`, does not authorize unrelated servers, and does not grant public publishing, deletion, account changes, or unrelated external mutation.

If Stitch is unavailable, unauthenticated, returns an error, or cannot complete the request, report `UNAVAILABLE` plus `FALLBACK_ACTIVE`, record the limitation briefly, and continue through project specifications → supplied references → selected verified design skills → local frontend implementation → browser critique → deterministic QA. Do not repeatedly retry the same failing MCP call. Stitch is optional and never turns a showcase run into `BLOCKED_REQUIRED`.

The browser verification model is deliberately additive:

```text
Playwright + axe = mandatory deterministic baseline
Antigravity browser tooling = interactive and visual verification
Manual inspection = final fallback
```

The Antigravity agent must inspect the live layouts and captured screenshots. Merely generating screenshot files does not satisfy visual QA.

## Repository-owned deterministic baseline

These checks do not depend on optional MCP access or globally installed skills.

| Check                              | Command             | Contract                                                                                                                                                                            |
| ---------------------------------- | ------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Formatting                         | `pnpm format:check` | Repository files match Prettier formatting.                                                                                                                                         |
| Documentation integrity            | `pnpm docs:check`   | Required documents and runtime contracts exist, `AGENTS.md` references them, local Markdown links resolve, and project readiness markers are coherent. Template mode remains valid. |
| Static code quality                | `pnpm lint`         | ESLint and Next.js rules pass without suppressing root causes.                                                                                                                      |
| Type safety                        | `pnpm typecheck`    | Strict TypeScript passes.                                                                                                                                                           |
| Browser and accessibility baseline | `pnpm test:e2e`     | Registered routes pass runtime, console, overflow, serious/critical axe, and screenshot coverage. Axe does not replace keyboard or focus reasoning.                                 |
| Static export                      | `pnpm build`        | Local responsive media variants and the Next.js `out/` export are produced; server-only requirements must fail or be classified as exceptions.                                      |
| Exported-site behavior             | `pnpm test:static`  | After the build, Wrangler Pages serves `out/` for direct routes, reloads, responsive images, and core interactions. See [`CLOUDFLARE.md`](CLOUDFLARE.md).                           |
| Aggregate gate                     | `pnpm qa`           | Formatting, docs, lint, types, Playwright/axe, one production export, and exported-site checks all pass in sequence.                                                                |

Playwright is mandatory baseline QA, not a fallback. Keep [`tests/e2e/routes.ts`](../../tests/e2e/routes.ts) aligned with `SITE.md` and add project-specific interaction assertions where acceptance requires them. Browser MCP, when available, adds exploratory and visual coverage; it does not reduce the Playwright obligation.

Generated evidence belongs under [`artifacts/qa/`](../../artifacts/qa/README.md). Review screenshots at the project-defined viewports and at relevant intermediate widths. A screenshot file that nobody inspected is not visual evidence.

## Execution modes and handoff

Direct Build, Concept Sprint, Teamwork criteria, platform entry points, and the reusable prompts live in [`RUNBOOK.md`](RUNBOOK.md). All modes use the same authority hierarchy and local completion gate.

If an optional capability is missing, note it once, use the matrix fallback, and continue. Stop only when the project explicitly requires an external capability, the current environment cannot supply it, and no safe local alternative can satisfy the owning specification. Report the exact missing capability, affected criterion, attempted fallback, and required user action.
